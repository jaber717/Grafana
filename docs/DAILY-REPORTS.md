# Daily network traffic reports

Two professionally designed A4-landscape PDFs, produced every morning from **Grafana panels** and delivered by e-mail and (optionally) Telegram:

| File | Source | What it answers |
|---|---|---|
| `Daily-NetFlow-YYYY-MM-DD.pdf` | Akvorado NetFlow in ClickHouse | How much traffic crossed the network edge yesterday, in which direction, who/what/where it came from, and how complete the data is |
| `Daily-Interface-Traffic-YYYY-MM-DD.pdf` | Zabbix interface items | How busy each configured link was, how close to its capacity, and where data is missing |

The reporting window is always the **previous complete calendar day in Asia/Riyadh, 00:00–24:00**, printed on every page. Both reports are independent: a day without NetFlow still produces a complete Interface report, and vice versa. Layout, wording and the NO DATA / PARTIAL behaviour are shown in [`docs/reports/examples/`](reports/examples/README.md); evidence, sizing and limits are in [`docs/reports/VALIDATION.md`](reports/VALIDATION.md).

## 1. How it works

```
 Grafana dashboards  ──►  Grafana image renderer  ──►  HTML pages  ──►  Chromium  ──►  PDF  ──►  e-mail / Telegram
 (NOC / Daily Reports)     (panel PNGs, exact size)     (KPIs, tables)   (print)
        ▲                                                    ▲
        └──── same queries ────── /api/ds/query (numbers) ──┘
```

* **Grafana is the reporting platform.** Every chart in the PDFs is a PNG rendered by Grafana from a real dashboard panel; nothing is redrawn by another charting library. The report code only places those images next to KPI cards and tables.
* **One query definition.** The dashboard panels and the KPI/table numbers are produced from the *same* SQL / Zabbix targets (`reports/lib/queries.mjs`, `dashboards.mjs`), executed through Grafana's `/api/ds/query`. A unit test proves the panels carry exactly the shared queries, so the picture and the number cannot disagree.
* **No Chromium on the Grafana server.** Panel rendering is done by the official *Grafana Image Renderer* (a separate container, pinned by digest). The PDF is printed with the Chromium inside the *same* pinned image, run rootless with Podman by the report job.
* **Dashboards** live in the folder **`NOC / Daily Reports`**; they are generated by `grafana-report build-dashboards` (the interface dashboard depends on your interface list). The seven operational dashboards are not touched, and `grafana-platform apply/verify` ignore this folder.

| Component | Runs on | Needs |
|---|---|---|
| Grafana 13.2.3 OSS (existing) | existing Grafana server | only the optional `[rendering]` setting (restart) — no Chromium |
| Grafana Image Renderer v5.12.6 | **separate renderer host** (recommended) | Podman, 2 vCPU / 4 GiB (measured: 350 MiB, 2.5 cores while rendering) |
| `grafana-report` + PDF printing | report host (may be the renderer host) | Node.js ≥ 18, Podman, ≥ 2 GiB free RAM (Chromium print peaks ≈ 1.1 GB) |

## 2. What the reports show

### Page structure (both reports)
1. **Executive Summary** — KPI cards, the main chart, key observations, collection/completeness.
2. **Traffic Analysis** — NetFlow: hourly volume, report day vs previous day, protocol mix, traffic by site and by ISP. Interfaces: one Grafana panel per interface (1–2 interfaces get full-width panels, 3–4 a 2×2 grid, more a 2×3 grid per page).
3. **Technical Details** — Top-10 tables, exporter / interface tables, missing-data indicators, data quality and methodology.

Every page carries the date, the period, the status badge (COMPLETE / PARTIAL / NO DATA), the data coverage and a footer with source and generation time.

### Data rules (so the numbers can be trusted)
* **NetFlow volume is sampled-flow estimate.** Estimated bytes = Σ `Bytes × SamplingRate`. When any exporter samples, labels say **(est.)**; unsampled exporters give observed volume. The first Key observation states the sampling.
* **Direction comes from verified interface boundary metadata** (external→internal = inbound, internal→external = outbound). Transit and unclassified flows are counted separately and are in neither direction. Nothing is guessed.
* **Exporters are listed separately and never summed**; a flow seen by two exporters appears in each exporter row. Top-N tables use only flows classified inbound/outbound.
* The Akvorado **demo exporter** (`::ffff:247.16.14.11`) is always excluded.
* **Per-IP / per-service tables read the raw flow table, which keeps 14 days.** For an older date the tables say so instead of showing nothing.
* **Interface rates come from Zabbix** (`Interface …: Bits received` / `Bits sent`, already converted from SNMP counters by Zabbix; a counter reset appears as a missing sample, never as zero or a spike). Averages use covered time; **utilisation = rate ÷ configured speed** and is **N/A when no speed is configured**. A sample above speed (+5 %) is excluded and counted — it usually means a wrong speed setting.
* **No grand total across interfaces.** Totals exist only for an explicitly configured *boundary* and only over intervals where all member interfaces reported; overlapping interfaces in one boundary make the configuration invalid.
* **Coverage** = share of the 288 five-minute intervals with data. ≥ 95 % is COMPLETE, below is **PARTIAL** (figures understate real traffic, and the report says so). No data at all is **NO DATA**: a designed page that shows what was checked and **no figures, never a zero**.
* **Previous-day comparison is shown only for a complete day** (an incomplete day is not comparable with a full one — the report says why instead of printing a percentage).
* **DEMO** data (layout examples) is always watermarked and bannered, filenames start with `DEMO-`, and the operational code path never reads it.

## 3. Install on RHEL 9.x

> Tested on **RHEL 9.6** (SELinux enforcing). Other 9.x releases are supported, not individually validated. Nothing in this guide changes the running Grafana until you decide to (step 2 needs a Grafana restart — do it in a change window).

### Step 0 — decide the topology
Recommended: a **separate host** (or VM) for the renderer + report job, 2 vCPU / 4 GiB RAM / 20 GB disk. Do **not** add Chromium to the existing 3 GiB Grafana server (see sizing in `VALIDATION.md`). A single host is acceptable only with ≥ 6 GiB RAM and 4 vCPU.

### Step 1 — the report host
```bash
git clone … && cd Grafana && sudo scripts/install-reports.sh --with-renderer --install-podman
# Offline hosts: install the offline bundle first (docs/OFFLINE.md) and load the renderer image (see "Offline installation")
```
This creates the `grafana-report` user, `/etc/grafana-platform/reports/`, `/var/lib/grafana-report/`, the systemd units and the `grafana-report` command (`/usr/local/sbin`, which `sudo` does not search: use the full path with `sudo`). The timer is installed **but not enabled**, and e-mail/Telegram stay **off**.

Prefetch the pinned image for the service user (rootless images and root images are separate stores):
```bash
cd / && sudo -u grafana-report env HOME=/var/lib/grafana-report/home XDG_RUNTIME_DIR=/run/grafana-report \
  podman pull docker.io/grafana/grafana-image-renderer@sha256:4b3d29a66c1dd11d513f8378907953b3c2c0c0535cbf5cf8fe83f7f398ae8b4c
```

### Step 2 — the renderer service and Grafana's `[rendering]` setting
1. The installer created `/etc/grafana-platform/reports/renderer.env` with a **random** `AUTH_TOKEN`. On a **separate renderer host** set `RENDERER_ADDR` to its LAN address (e.g. `10.0.0.20:8081`) and restrict TCP 8081 to the Grafana server with firewalld; keep `127.0.0.1:8081` if Grafana runs on the same host.
2. `sudo systemctl enable --now grafana-image-renderer` (root Podman; it needs the image in the **root** store: `sudo podman pull …` or `grafana-report load-image`).
3. On the Grafana server put the same token in a file (`install -m 0640 -o root -g grafana … /etc/grafana-platform/secrets/renderer.token`) and set in `env/platform.env`:
   ```
   RENDERING_SERVER_URL=http://RENDERER-HOST:8081/render
   RENDERING_CALLBACK_URL=https://YOUR-GRAFANA-URL/
   RENDERING_TOKEN_FILE=/etc/grafana-platform/secrets/renderer.token
   ```
   then `sudo grafana-platform install` (renders a `[rendering]` section with `renderer_token = $__file{…}`, **restarts Grafana**). Grafana 13 refuses to start with the default renderer token; the token is never written into `grafana.ini`.

### Step 3 — tokens
Create two Grafana **service accounts** (Administration → Service accounts, or the API):

| Account | Role | Used for |
|---|---|---|
| `report-job` | **Viewer** | the daily job: read the two dashboards, query the two datasources, render panels |
| `report-editor` | Editor (on folder `NOC / Daily Reports`) | only `build-dashboards --apply` (can be a one-time token) |

Write each token to a file (`install -m 0600 -o grafana-report -g grafana-report`). The job never needs more than Viewer.

### Step 4 — settings and interfaces
```bash
sudoedit /etc/grafana-platform/reports/report.env        # GRAFANA_URL, token file, EMAIL_/TELEGRAM_ settings (both OFF by default)
sudoedit /etc/grafana-platform/reports/interfaces.yaml   # which interfaces to report (see §5)
```
Reference: [`config/reports/report.env.example`](../config/reports/report.env.example) is fully commented. Key points: secrets are **only** referenced as `*_FILE` paths; `CHROMIUM_CMD` defaults to the pinned image under rootless Podman; nothing is sent until `EMAIL_ENABLED=true` / `TELEGRAM_ENABLED=true` and the recipients are listed.

### Step 5 — install the dashboards, then check everything
```bash
sudo -u grafana-report /usr/local/sbin/grafana-report build-dashboards --apply --token-file /etc/grafana-platform/reports/editor.token
sudo -u grafana-report /usr/local/sbin/grafana-report check-config
```
`check-config` validates the settings, the interface list, Chromium, Grafana reachability and that **both dashboards are current** (see "Revision guard"). It prints `[ OK ] / [FAIL]` per check.

### Step 6 — generate by hand, then test delivery
```bash
sudo -u grafana-report /usr/local/sbin/grafana-report generate --date 2026-10-11     # PDFs only; nothing is sent
sudo -u grafana-report /usr/local/sbin/grafana-report test-delivery --email --to you@example.com   # DEMO sample PDFs, marked [TEST]
```
Review the PDFs in `/var/lib/grafana-report/out/<date>/`.

### Step 7 — enable the schedule (only when you have approved real delivery)
```bash
sudo /usr/local/sbin/grafana-report schedule set 07:00      # default; Asia/Riyadh
sudo /usr/local/sbin/grafana-report schedule enable
```

### Offline installation
1. On a connected machine: `tools/build-offline-bundle.sh` (Grafana RPM, plugins, Node.js — see `OFFLINE.md`) and `tools/build-renderer-bundle.sh` (the renderer image, ≈ 550 MB, digest verified).
2. On the isolated host: `sudo grafana-report load-image grafana-image-renderer-*.tar.gz --as-user grafana-report` and (renderer host) `sudo grafana-report load-image grafana-image-renderer-*.tar.gz`. The loader checks the image **ID** against the one this release expects and tags it `localhost/grafana-image-renderer:pinned`.
3. Use `localhost/grafana-image-renderer:pinned` instead of the registry reference in `CHROMIUM_CMD` and `renderer.env` (`podman run --pull=never` is used by the tests; the registry digest cannot resolve offline).

## 4. Configuration reference

### `report.env` (selected keys)
| Key | Meaning |
|---|---|
| `GRAFANA_URL`, `GRAFANA_TOKEN_FILE` | Grafana base URL and the Viewer token file |
| `REPORT_KINDS` | `netflow,interface` (either or both) |
| `INTERFACES_FILE` | the YAML in §5 |
| `CHROMIUM_CMD` | program + arguments (no shell); placeholders `{workdir}` `{uid}` `{gid}`; fully qualified image names only |
| `OUTPUT_DIR`, `STATE_DIR`, `LOG_FILE`, `RETENTION_DAYS` | files, delivery ledger, JSON log, how long daily folders are kept (45) |
| `EMAIL_ENABLED`, `EMAIL_FROM`, `EMAIL_TO`, `EMAIL_SUBJECT_PREFIX` | recipients are an explicit comma-separated list |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURITY` (`none`/`starttls`/`tls`), `SMTP_USER`, `SMTP_PASSWORD_FILE`, `SMTP_TLS_CA_FILE` | credentials are refused over `none` |
| `TELEGRAM_ENABLED`, `TELEGRAM_BOT_TOKEN_FILE`, `TELEGRAM_CHAT_ID`, `TELEGRAM_API_BASE` | the API base is configurable only for tests |
| `RETRY_ATTEMPTS`, `RETRY_BASE_SECONDS`, `RETRY_MAX_SECONDS`, `NOTIFY_ON_FAILURE` | exponential backoff; one "generation failed" notice per day |

### `interfaces.yaml`
No Zabbix item id appears anywhere; items are selected by **device (Zabbix host name) and item name**.

```yaml
groups:
  - id: wan
    title: WAN uplinks
interfaces:
  - site: SITE-A              # label in the report
    device: SITE-A            # Zabbix host name
    interface: Gi0/0
    description: TO-SAIX-A-Gi0/1
    speed: 1G                 # 100M, 1G, 10Gbps or bit/s; empty = utilisation N/A
    traffic_direction: provider-facing   # received = INBOUND (default) | customer-facing: received = OUTBOUND
    group: wan
    boundary: SITE-A-WAN      # optional: totals only inside a boundary
    include: true             # MANDATORY true/false: nothing is ever included implicitly
    # overlaps_with: [SITE-A:Po1]   # LAG members / sub-interfaces: overlapping interfaces in one boundary are refused
    # rx_item / tx_item: only if the Zabbix item names differ from "Interface <if>(<description>): Bits received/sent"
```
The shipped example starts with the **SITE-A and SITE-B WAN interfaces** that exist in the LAB Zabbix; STC and MOBILY are listed as `include: false` examples.

## 5. Onboarding real interfaces (read-only discovery)
```bash
export ZABBIX_URL=https://zabbix.example.com/api_jsonrpc.php ZABBIX_TOKEN_FILE=/root/zbx-readonly.token
grafana-report discover --out candidates.yaml          # every interface with Bits received/sent items; ALL include: false
grafana-report discover --compare /etc/grafana-platform/reports/interfaces.yaml   # does my mapping match Zabbix?
```
Only `item.get` is called with a **read-only** Zabbix API token. Copy the entries you want into `interfaces.yaml`, choose group/boundary, verify the suggested speed, set `include: true`, then run `build-dashboards --apply` and `check-config`. No reporting code changes are needed.

**Revision guard.** Each generated dashboard carries a `rev:<fingerprint>` tag of its panel definitions. If the interface list (or the release) changes and the dashboards are not re-applied, the job stops with *“dashboard … is out of date: run build-dashboards --apply”* instead of rendering the wrong panels.

## 6. Daily operation

| Command | Purpose |
|---|---|
| `grafana-report run` | what the timer runs: generate both reports, deliver to every enabled channel |
| `grafana-report generate [--date D] [--kind netflow\|interface] [--keep-html]` | manual **Generate Report**; never sends |
| `grafana-report deliver [--date D] [--force]` | send already generated PDFs |
| `grafana-report test-delivery [--email] [--telegram] [--to a@x,b@y]` | manual **Test Delivery** with clearly marked DEMO sample PDFs |
| `grafana-report check-config` | pre-flight; also shows dashboard revisions |
| `grafana-report status [--date D]` | last run summary and the delivery ledger |
| `grafana-report schedule show\|set HH:MM\|enable\|disable` | the daily timer |
| `grafana-report load-image FILE [--as-user U]` | offline renderer image import |

Exit codes: `0` ok · `1` configuration error · `2` generation failed · `3` delivery failed or partial. Everything is logged as JSON lines to the journal and `LOG_FILE` (no secrets).

**Duplicate protection.** A delivery ledger (`STATE_DIR/ledger/<date>.<channel>.json`) records what was delivered (each e-mail recipient; each Telegram part). A second run — timer fired twice, manual repeat — finds every enabled channel already delivered and **stops before querying Grafana**; `--force` regenerates and resends deliberately. A retry after a partial failure resends only what is missing; a recipient the server rejected permanently (550) is not retried. A lock file prevents two simultaneous runs for the same day.

**Retries.** Transient failures (network, Grafana 5xx/429, SMTP 4xx, Telegram 429/5xx) are retried with exponential backoff (Telegram's `retry_after` wins when larger). Permanent failures (wrong token, 401/403, bad chat id, SMTP 5xx, invalid layout) are not retried. If generation fails after retries the run exits 2 and one **“GENERATION FAILED”** notice is e-mailed (once per day, no attachment). The next day's run is independent.

**Degradation.** If one of the four raw-table Top-10 queries fails (e.g. query timeout on a very busy network) the report is still produced; that table says *not available* and the observations say so. A failure of any other query, or a Grafana outage, stops the run.

## 7. Scheduling
`grafana-report.timer` fires at **07:00 Asia/Riyadh** (= 04:00 UTC, no DST) with `Persistent=true`: if the host was down at 07:00 the run happens at the next start (idempotent, so it cannot double-send). `grafana-report schedule set 07:30` writes a drop-in (`/etc/systemd/system/grafana-report.timer.d/schedule.conf`) after validating it with `systemd-analyze calendar`; the shipped unit is never edited. The timer is **disabled until you enable it**.

## 8. E-mail and Telegram
**E-mail**: one message per day to the configured list (multiple recipients supported), HTML summary (status chips, headline figures, observations, attachment list) + plain-text alternative + the two PDFs. STARTTLS and implicit TLS verify the server certificate (`SMTP_TLS_CA_FILE` for a private CA); credentials are never sent over `none`; a certificate that does not verify aborts before any password is sent. Test with Mailpit or any SMTP test server: only `SMTP_HOST/PORT/SECURITY` change.

**Telegram**: create a bot with @BotFather, put its token in `TELEGRAM_BOT_TOKEN_FILE`, add the bot to the chat and set `TELEGRAM_CHAT_ID`. Per day: one summary message (HTML parse mode, ≤ 4096 chars) + one document per PDF. Rate limits (`429 retry_after`) are honoured; the bot token never appears in logs or errors.

## 9. Security
* Least privilege: Viewer token for the job; Editor only for installing dashboards; read-only Zabbix token for discovery; no ClickHouse or Zabbix credential in the report tooling (Grafana owns them).
* Secrets only in `0600` files; `check-config` warns about group/world-readable secret files; `*_FILE` keys everywhere; no secret in the env file, the journal or the PDFs.
* The renderer listens on loopback (or a firewalled LAN address) behind a token; the container runs with `--cap-drop ALL`, `no-new-privileges`, a read-only root filesystem and memory/CPU/PID limits.
* The service unit uses `ProtectSystem=strict`, `ProtectHome`, `PrivateTmp`, `ProtectControlGroups`, `UMask=0027`. Seccomp-based directives (`ProtectKernel*`, `RestrictNamespaces`, `NoNewPrivileges`, …) are deliberately **not** used: they make systemd imply no-new-privileges, which breaks the setuid `newuidmap` rootless Podman needs (verified by bisection on RHEL 9.6). The container is Chromium's sandbox.
* All message and report text is HTML-escaped; header injection in e-mail fields is rejected.
* Nothing is sent to anyone not listed in `EMAIL_TO` / the configured Telegram chat; real delivery is **off** until enabled.

## 10. Troubleshooting
| Symptom | Cause / fix |
|---|---|
| `dashboard … out of date` | interface list or release changed: `build-dashboards --apply` |
| `render panel N: got … px, expected … px` | renderer minimum viewport: set `BROWSER_MIN_WIDTH=300`, `BROWSER_MIN_HEIGHT=100` (the shipped unit does) |
| PDF step: `newuidmap: write to uid_map failed` | a seccomp-based hardening directive was added to the unit — remove it |
| PDF step: `Failed To Create Data Directory` / permission denied | run the container as the host uid (`--user {uid}:{gid}`) with `HOME={workdir}` (the default `CHROMIUM_CMD`) |
| Podman `short-name resolution enforced` | use a fully qualified image (`docker.io/…`) |
| Podman `database … does not match` / runtime lock errors | the runtime directory path must stay `/run/grafana-report` (tmpfiles.d creates it) |
| `layout check failed … overflows` | too much content for a page; report it (the guard refuses to print a cropped PDF) |
| Grafana won't start after adding `[rendering]` | the renderer token must not be the default: set `RENDERING_TOKEN_FILE` |
| Interface shows NO DATA though Zabbix has data | `discover --compare`: item name / host name mismatch (visible host name vs technical name) |
| `sudo grafana-report: command not found` | use `/usr/local/sbin/grafana-report` (sudo's secure_path) |

## 11. Upgrade and rollback
Update the release directory, run `check-config`; the revision guard tells you whether `build-dashboards --apply` is needed. The renderer image is pinned by digest/ID: change it only together with a validation run (`tests/rhel/*`). To roll back, restore the previous release directory and re-apply that release's dashboards. State (`STATE_DIR`) is plain JSON and is not migrated.
